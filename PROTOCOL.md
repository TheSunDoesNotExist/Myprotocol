# Экспериментальный протокол v5

v5 несовместим с v1–v4: клиент и сервер нужно обновлять вместе, даже с выключенным SRTL. Перед кадрами
обязателен HTTPS CONNECT: TLS 1.3/TCP с ALPN `http/1.1` или HTTP/3 на QUIC/UDP
с ALPN `h3`. Клиент проверяет сертификат и имя сервера. 0-RTT отключён.

## HTTP carrier

После проверки TLS клиент отправляет HTTP/1.1 `CONNECT relay.internal:443`
с `Host: relay.internal:443` и `Proxy-Authorization: Bearer <shared key>`.
Только после `200 Connection Established` идут внутренние кадры, без HTTP body
framing, Content-Length или Transfer-Encoding.

В HTTP/3 используется обычный CONNECT, не extended CONNECT: заголовки `:method`
и `:authority` плюс тот же `proxy-authorization`, без `:scheme`, `:path`, `:protocol`.
Ответ — `:status: 200`, без Content-Length; внутренние кадры передаются в HTTP/3 DATA
единственного двунаправленного stream 0. Три однонаправленных служебных stream
HTTP/3/QPACK имеют фиксированный лимит по 4096 байтов. Динамические QPACK-таблицы
и blocked streams отключены; заголовки ограничены 8192 байтами, дубликаты запрещены.

`relay.internal:443` — фиксированное имя внутри протокола, не DNS-запрос и не
разрешение подключаться к произвольному адресу. Назначение задаётся сервером.
Неавторизованный CONNECT получает HTTP 404 без создания сессии. GET/HEAD `/`
возвращает статическую страницу. Срок чтения HTTP/1.1 заголовков — 3 секунды;
общий срок авторизации QUIC — 5 секунд от создания канала.
В TCP общий deadline до проверки ключа — 5 секунд от accept, включая TLS и HTTP.
До выделения TLS проверяются квоты: 64 соединения, 32 до авторизации, 8 с одного IP.
Такие же квоты отдельно применяются к QUIC. Выходной QUIC-буфер ограничен
256 КиБ, `drain()` ждёт снижения до 128 КиБ; при переполнении/таймауте канал
закрывается, а сессия сохраняет надёжные события для восстановления.
Ключ проверяется до запуска внутреннего протокола и затем повторно в HELLO/PROBE.
Все эти поля находятся внутри проверенного шифрованного канала; в лог не попадают.

Собственный ALPN отсутствует. В основном IP-only режиме SNI отсутствует;
hostname-режим низкоуровневого API без ECH раскрывает SNI. Fingerprint
стека, IP и статистика трафика остаются наблюдаемыми.

## Обязательный ECH (опциональный режим)

`--ech-config`/`--ech-keys` включают внешний gateway на Go TLS/QUIC.
Внешний TLS требует принятия ECH, проверки сертификата внутреннего DNS-имени
и ключа CONNECT. До этого внутренний поток и PSK не передаются. Публичное имя
ECHConfig должно отличаться от внутреннего; конфиг закреплён локальным файлом.
Внешний адрес задаётся IP, чтобы не выдавать внутреннее имя через DNS bootstrap.
Повтор без ECH, автоматическая замена pinned config и 0-RTT не применяются.

Внешние HTTPS CONNECT / HTTP/3 DATA несут **внутренний TLS 1.3/HTTP/1.1 CONNECT**,
в котором передаются кадры v5 и проверки CA/имени/PSK/поколения. На UDP
надёжность обеспечивает внешний QUIC; loopback между процессами не содержит
открытой полезной нагрузки. Внутренние серверные порты привязаны к loopback,
HTTP CONNECT backend разрешает только к этим фиксированным локальным портам.
На проводе остаются стандартные HTTP ALPN и публичный ECH SNI, без собственного
имени протокола. Fingerprint Go и временной рисунок сохраняются.

Native gateway имеет свои bounded flow-control buffers и квоты; точные пределы,
сертификаты, формат файлов и запуск описаны в [ECH.md](ECH.md).

## Кадр и аутентификация

Кадр: `uint32_be length`, затем JSON UTF-8 длиной 1..32768 байтов. DATA — base64,
после декодирования максимум 16384 байта. Sequence, offsets и StreamID — целые
числа менее 2^63; sequence и StreamID начинаются с 1. Типы и размеры проверяются.

Для новой сессии клиент отправляет:

```json
{"type":"hello","version":5,"key":"<64 hex>","generation":1}
```

Для возобновления добавляются `session` (128 случайных бит, 32 hex) и `secret`
(256 случайных бит, 64 hex). `generation` растёт с каждой попыткой присоединения;
сервер принимает только значение больше ранее зарезервированного.

Ответ:

```json
{"type":"welcome","version":5,"session":"<SessionID>","secret":"<resume secret>","transport":"<TransportID>","generation":1}
```

Клиент проверяет версию, идентичность сессии и поколение и подтверждает канал:

```json
{"type":"ready","generation":1,"transport":"<TransportID>"}
```

Сервер проверяет подтверждение и поколение, отправляет
`{"type":"ready_ok","generation":1}`, затем снова проверяет поколение после
ожидания drain и синхронно привязывает транспорт к Session Manager.
До этого прежний транспорт остаётся активным. Клиент привязывает канал после READY_OK.
Контроллер сериализует переключения и синхронно публикует нового владельца до
ожидания остановки старого reader; запоздалый автоматический план выбора отбрасывается.
Между двумя сетевыми узлами нет атомарного commit: потеря последнего подтверждения
устраняется новой попыткой восстановления в рамках того же срока удержания.
Если новая сессия ни разу не была привязана к транспорту и её READY не подтверждён,
она освобождается сразу после отказа попытки. При более новом зарезервированном
поколении старая попытка не освобождает сессию, принадлежащую новой попытке.

Запоздалый reader вытесненного транспорта больше не может изменять состояние.
Недействующий SessionID/секрет получает `expired`; неверный ключ получает `rejected`,
а старое поколение — `rejected` с `reason: "stale_generation"`. Клиент также проверяет,
что его попытку не вытеснила более новая, прежде чем применить READY_OK. Устаревшая
попытка закрывается без смены владельца и не считается компрометацией ключа.
При отказе аутентификации/сертификата кандидат изолируется до перезапуска клиента;
проверенный активный канал сохраняется. При отсутствии любых доверенных путей
передача останавливается; plaintext-fallback не существует.
Сервер не создаёт замену истёкшей сессии под видом успешного восстановления.

## Пробы пути

На отдельном проверенном TLS/QUIC канале разрешено до четырёх запросов:

```json
{"type":"probe","version":5,"key":"<shared key>","nonce":"<32 random hex>"}
```

Ответ `{"type":"probe_ok","version":5,"nonce":"<тот же nonce>"}`.
Пробы аутентифицированы, не выделяют Session Manager и не переключают его транспорт.
Клиент делает три запроса на альтернативный канал, измеряя application RTT, и закрывает соединение.
В клиенте 0.3.0 такие пробы запускаются после установки первой сессии. Начальное
подключение и восстановление выполняют полный hello/ready без предварительной пробы.
Активный путь измеряется ping/pong внутри уже аутентифицированной сессии.
Серверный QUIC-канал имеет 5 секунд на проверку общего ключа от создания соединения,
даже если первый stream так и не открыт. QUIC PING не продлевает этот deadline.

## Надёжные события

SRTL дополняет DATA **после JSON** пробелами внутри зашифрованного канала; uint32 length
учитывает эти пробелы. Не более 512 байтов trailing whitespace; общий MAX_FRAME прежний.
После JSON parsing padding не попадает в события, offsets или application-сокет.
Настройка локальная, по направлению; v5 всегда умеет принимать SRTL независимо от
своего флага отправки. После авторизации/READY разрешён также отдельный кадр
`{"type":"cover"}` с padding до полной длины 256/384/512 байт, включая uint32.
Другие поля, неподдерживаемая длина или превышение RX token bucket (8 КиБ burst,
2 КиБ/с refill на сессию) считаются нарушением протокола.
Cover не имеет seq/ACK, не меняет offsets, не продлевает heartbeat и не ставится
в Session replay queue. Сам TLS/QUIC carrier может повторять байты для своей доставки.
Предыдущий хвост отменяется при смене канала; новая реальная передача может породить
новый хвост в пределах общего cooldown. Подробная политика: [TRAFFIC_SHAPING.md](TRAFFIC_SHAPING.md).

Для каждого направления сессии есть общий монотонный `seq`. До 16 событий находятся
в передаче без ACK, ещё до 64 ждут отправки. Получатель имеет ограниченную очередь
на 16 событий и применяет их по порядку. При новом транспорте неподтверждённые
события повторяются неизменными. Каждая sequence применяется один раз.

| type | Поля помимо type/seq/stream | Действие |
|---|---|---|
| `open` | — | Принимает запрос и отдельно устанавливает сокет к `--target` |
| `data` | `offset`, `data` | Принимает байты в ограниченный буфер потока |
| `fin` | `offset` | Ставит TCP half-close после накопленных байтов |
| `reset` | — | Прерывает поток после ошибки сокета |

OPEN разрешён от клиента. Offset относится к одному направлению конкретного потока.
Для новой sequence DATA/FIN должен иметь ровно ожидаемый offset. Нарушение порядка,
неизвестный поток, DATA после FIN или неверный ACK закрывают сессию с ошибкой.

```json
{"type":"ack","seq":8,"stream":2,"offset":16384}
```

ACK накопительный: подтверждает применение всех sequence до указанной включительно.
После DATA это означает принятие байтов в ограниченный буфер Session Manager,
не запись в сокет назначения, обработку приложением или сохранение на диск.
OPEN подтверждает приём запроса, а подключение назначения выполняется независимо;
ошибка подключения даёт RESET. Offset DATA/FIN — следующая позиция принятых байтов;
OPEN/RESET — 0. Отправитель сверяет sequence, поток и offset соответствующего события,
после чего освобождает все подтверждённые события.
При RESET оставшиеся события уже прерванного потока могут подтверждаться и
отбрасываться, чтобы освободить очередь других потоков; операция приложения
при этом считается прерванной, а не успешно завершённой.

Повтор принятого события получает последний ACK без повторной записи. Уже поставленное
в очередь событие повторно не ставится. Каждый поток имеет отдельную задачу доставки
в сокет и отдельный байтовый буфер; они принадлежат сессии и переживают смену транспорта.
FIN исполняется только после записи накопленных данных и drain. Ошибка записи даёт
RESET. OPEN и FIN повторяются наравне с DATA, без повторного открытия назначения.

## Окна потоков

Первоначальный credit каждого направления потока — 65536 байтов. Отправитель читает
локальный сокет только в пределах доступного credit. После drain при записи данных
получатель увеличивает абсолютную разрешённую позицию:

```json
{"type":"window","stream":2,"limit":131072}
```

`limit = записанные_в_сокет_байты + 65536`. Получатель DATA проверяет этот предел до
расширения буфера. Отправитель принимает только целый limit, не превышающий уже
поставленные им в отправку байты плюс окно. Старые/повторные grants не суммируются.
Таким образом, замерший сокет удерживает максимум 64 КиБ данных своего потока,
не блокируя приём и подтверждения остальных потоков.

WINDOW не имеет sequence и передаётся по тому же защищённому надёжному каналу.
Обновления coalesce по StreamID, их очередь ограничена количеством потоков. При смене
транспорта актуальные credits всех уже получавших данные потоков отправляются снова.
Потеря WINDOW на границе обрыва не оставляет поток навсегда без credit.
Первое WINDOW отправляется только для потока, уже известного обеим сторонам.

## Живость и гарантия восстановления

`ping` и `pong` содержат случайный `nonce` (16 hex), не имеют sequence и не
подтверждают данные. Ответ на свой nonce позволяет измерить RTT heartbeat.
Heartbeat — 1 секунда, таймаут чтения — 4 секунды, срок хранения отсоединённой
сессии — по умолчанию 30 секунд с момента обнаружения отказа.

Сохраняются обе очереди, принятые sequence, offsets, состояния FIN/RESET и сокеты.
Сверка состояния после восстановления реализована повтором события и ACK.
Гарантия касается порядка и отсутствия повторной записи в живые сокеты. Она не
обеспечивает exactly-once для бизнес-операций при падении процесса или отказе
назначения. По истечении срока сессия закрывается, CLI клиента возвращает ошибку.
Аварийные локальные TCP-сокеты закрываются с RST, чтобы частичный результат не
выглядел штатным EOF. Успешные FIN/half-close сохраняют обычную семантику TCP.

Шифрование и replay protection сетевых пакетов обеспечивает TLS/QUIC. Дедупликация
событий сессии — отдельный механизм для корректного восстановления, не замена AEAD.
Перенос открытого исходящего TCP-сокета на другой IP не реализован: для двух VPS
нужен сохраняющийся узел выхода, поскольку идентичность TCP-соединения зависит
от адресов и портов ([RFC 9293](https://www.rfc-editor.org/rfc/rfc9293.html)).
