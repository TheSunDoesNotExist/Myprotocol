# Аудит Myownvpn v2 — 2 ноября 2026

**Статус исправлений после аудита:** A01–A07 исправлены и имеют regression-проверки
в стандартном прогоне через `test_hardening.py`. Для A03 проверяются и серверный

Прямой ClientHello-тест по-прежнему явно фиксирует видимость SNI без ECH.
Полная схема и запуск: [ECH.md](ECH.md). Fingerprint браузера не воспроизводится.

**A01. Лимит 96 КиБ проверяется после неограничиваемой им сборки QUIC-данных**

Место: `transports.py:150`, `transports.py:155`, конфигурация `quic_config()`.
Внутри закреплённого aioquic: `QuicStreamReceiver.handle_frame()` и
`QuicConnection._write_stream_limits()`.

Проверка адаптера срабатывает только при событии `StreamDataReceived`. Если
злоумышленник оставляет пропуск в начале потока и посылает последующие offsets,
библиотека сначала собирает их в собственном reassembly-буфере. Событие приложения
не возникает, поэтому не запускаются ни проверка 96 КиБ, ни чтение HELLO с его
таймаутом. Лимиты QUIC flow control в этой интеграции автоматически увеличиваются
по принятому highest offset, а не по потреблению данных нашим приложением.

В локальном тесте партнёр завершил обычный QUIC handshake, **не знал MYVPN_KEY и
не отправлял HELLO**, оставил байт 0 непереданным и накопил 256 КиБ в reassembly.
Проверка ключа не запускалась. Это демонстрирует обход лимита; полный OOM и нагрузка
на публичный сервер не запускались. Вывод о возможности дальнейшего роста основан
на механизме увеличения receive credits в исходниках библиотеки.

Исправление: учитывать reassembly и все остальные receive-буферы в едином бюджете
соединения; выдавать receive credits согласно фактическому потреблению; ограничить
буфер и время до аутентификации ещё на уровне QUIC. Проверки после выдачи application
events недостаточно. Если текущий backend не предоставляет подходящих стабильных API,
выбор другого QUIC backend следует оценить раньше дальнейшего усложнения адаптера.
Это проблема нашей интеграции; здесь не утверждается наличие нового CVE в aioquic.

**A02. Сбой резервного UDP превращён в глобальное прекращение доверенной сессии**

Места: `transports.py:147`, `transports.py:246`, `tunnel.py:616`, `tunnel.py:677`.

Любой `ConnectionTerminated` до завершения handshake с кодом 0x100..0x1ff
расценивается как `security_failure`. Код ошибки партнёра не является доказательством
локально установленной ошибки сертификата. В QUIC Initial нет секретной аутентификации
партнёра: ключи защиты Initial выводятся из доступного CID. Это прямо обсуждается
в [RFC 9001, §9.3](https://www.rfc-editor.org/rfc/rfc9001.html#section-9.3).

Контролируемый UDP-партнёр без сертификата и ключа отправил Initial CONNECTION_CLOSE
с TLS-подобным кодом. Клиент преобразовал его в SecurityError; обработчик измерений
закрыл уже работающую TLS/TCP-сессию. Реальный наблюдатель, способный читать и
инъецировать UDP-пакеты на пути, получает способ повлиять на TCP через резервный путь.
Аудит не утверждает, что произвольный off-path узел может угадать CID и выполнить
это без наблюдения трафика.

Исправление: отклонять и изолировать недоверенный **кандидатный канал**, сохраняя
действующий успешно аутентифицированный канал. Ошибку сертификата следует фиксировать
отдельно от непроверенного удалённого кода закрытия. Это сохраняет fail-closed:
непроверенному каналу не передаются данные; plaintext-fallback по-прежнему запрещён.
При отсутствии доверенных путей передача останавливается. Политика «закрыть всё при
любом сигнале с любого пути» может быть отдельным осознанным режимом, но не нужна
для сохранения шифрования исправного соединения.

**A03. Проверка поколения находится перед await, после которого владелец меняется**

Место: `tunnel.py:496` — проверка, `tunnel.py:498` — await, `tunnel.py:499` — attach.

Воспроизведение: поколение 2 прошло проверку и остановилось в `ready_ok` drain;
поколение 3 завершило присоединение; затем поколение 2 продолжило выполнение и
вызвало attach. Сессия хранит generation=3, но активным оказался writer поколения 2.
Ранее добавленный fencing reader не предотвращает неправильную смену самого владельца.

Исправление: повторная проверка владельца/поколения непосредственно перед attach
без await между проверкой и изменением владельца. Резервирование и commit должны
иметь согласованный порядок. Если используется lock, нельзя держать его на всё
ожидание удалённого READY, позволяя медленному клиенту блокировать новые попытки.
Нужны отдельные тесты потери READY_OK, отмены подключения и трёх конкурирующих попыток.
Для этой гонки требуются корректные права восстановления; перехват сессии без ключей
этим тестом не продемонстрирован.

**A04. QUIC handshake не ограничен сроком аутентификации приложения**

Места: `transports.py:186`, `transports.py:257`, `tunnel.py:443`.

HELLO timeout начинается после первого события данных QUIC-stream. Партнёр может
вообще не открывать поток с данными и поддерживать соединение транспортными PING.
QUIC Retry подтверждает достижимость адреса, но не владение ключом приложения.

Локальная проверка удержала такой канал более 6 секунд; Session Manager для него
не создавался, обработчик авторизации не запускался. Из кода следует, что 64 таких
канала займут глобальный лимит и не позволят новым клиентам подключиться. Заполнение
всех 64 слотов в рамках проверки не запускалось.

Исправление: самостоятельный deadline до подтверждения ключа с момента создания
канала/handshake, который нельзя продлевать PING. Отдельные квоты и rate limits
для новых, неавторизованных и авторизованных каналов; бюджет на адрес и глобальный
бюджет; защита TLS-handshake TCP средствами поддерживаемого frontend/ОС.

**A05. Обрыв может быть принят приложением за успешное окончание результата**

Места: `tunnel.py:62`, `tunnel.py:115`, `tunnel.py:404`.

`transport.abort()` не гарантирует TCP RST в используемой среде. Воспроизведение
передало приложению частичный ответ и закрыло сессию с ошибкой; приложение увидело
обычный EOF. Протоколы с Content-Length/хешем могут выявить недостающие байты,
а произвольный протокол с завершением по EOF — принять неполный ответ за законченный.
Ненулевой код CLI клиента не передаёт ошибку в уже подключённое приложение.

Исправление: различать штатный FIN и аварийный reset на локальном application-сокете;
реализовать и проверить abortive close для каждой целевой ОС. Для уже открытого
сырого TCP-потока нельзя добавить текст ошибки в полезную нагрузку. Нельзя выдавать
аварийный FIN за штатное завершение. Проверить Windows и Linux, а также ситуацию
частично отправленных данных; окончательное поведение зависит от сокетного стека.

**A06. Публикация результатов ждёт самый медленный путь**

Место: `tunnel.py:612`.

`asyncio.gather()` возвращает все измерения только после завершения последнего.
Успешный TCP может ждать таймаута UDP и cleanup. При допустимом `--grace 1` этот
барьер способен истечь раньше, чем разрешит использовать уже проверенный TCP.
Воспроизведение подставляет контролируемые длительности проб и подтверждает, что
connect не вызывается при уже полученном успешном TCP-результате.

Исправление: публиковать результаты независимо; сначала использовать доступный
проверенный путь, затем уточнять оценку. Принцип короткой задержки и параллельных
кандидатов можно заимствовать из [Happy Eyeballs, RFC 8305](https://www.rfc-editor.org/rfc/rfc8305.html),
адаптировав его к TCP/QUIC. Текущая реализация также берёт только первый результат
DNS для UDP (`transports.py:227`); нужны попытки альтернативных A/AAAA-адресов.

**A07. Медленный сокет назначения блокирует всю сессию**

Места: `tunnel.py:202`, `tunnel.py:323`, `tunnel.py:369`.

У сессии один неподтверждённый frame на направление, а ACK ждёт `drain()` конкретного
потока. Если назначение перестало читать, другие потоки тоже не продвигаются.
Heartbeats могут продолжать работать, поэтому транспорт считается исправным.
Переключение TCP → UDP сохраняет ту же зависшую задачу доставки и проблему не решает.
Проверка подтверждает сохранение зависшего delivery без ACK после миграции.

Производительность stop-and-wait примерно ограничена 16384/RTT байт/с: при RTT 100 мс
это около 160 КиБ/с полезных данных на направление, до накладных расходов и потерь.
Это расчёт архитектурного предела, не результат WAN-бенчмарка.

Исправление: независимые окна, credits, receive-очереди и offsets/ACK для потоков;
отдельные задачи доставки; справедливый планировщик; обособленный control channel.
Семантику ACK нужно явно выбрать: принятие в ограниченный буфер Session Manager или
запись в исходящий сокет. В обоих случаях отказ назначения должен давать reset,
а не ложное успешное завершение. На QUIC имеет смысл отдельный транспортный stream
для каждого логического потока с аутентификацией control-stream до допуска остальных.
На TCP останется транспортный head-of-line при потере пакетов, но медленное приложение
не должно дополнительно блокировать другие application-потоки.

Отдельное ограничение: 128 потоков считаются за всю жизнь сессии. Это может быстро
ограничить браузерные подключения. Нужны безопасное освобождение завершённых
состояний, ограниченные tombstones и автоматический жизненный цикл сессии.

**A08. Текущий handshake сам сообщает имя протокола**

Места: `transports.py:15`, `tls_client()`, `quic_config()`, `tunnel.py:578`.

Проверка реального ClientHello показала видимые `myownvpn/2` и DNS-имя сервера.
QUIC Initial тоже не скрывает ClientHello от наблюдателя, умеющего вывести Initial
keys. Это не расшифровка application DATA; это обнаружение типа соединения.

Дополнительно видны регулярные подключения-пробы двух транспортов раз в 5 секунд,
heartbeat раз в секунду, размеры и временные зависимости. Состав TLS-расширений и
поведение QUIC отличаются между стандартным OpenSSL и aioquic. Даже порт 443 сам по
себе не делает этот трафик обычным HTTPS. Случайные SessionID внутри шифрования здесь
не помогают наблюдателю и не устраняют внешние признаки.

**Как повышать скрытность с сохранением безопасности**

1. Добавить настоящий HTTPS carrier на TCP: HTTP/2 CONNECT или другой реально
   реализованный стандартный HTTP/WebSocket transport. На UDP рассмотреть настоящий
   [HTTP/3 CONNECT](https://www.rfc-editor.org/rfc/rfc9114.html#section-4.4) для надёжных
   байтовых потоков. Нельзя только объявить `h2`/`h3`,
   продолжив отправлять несовместимый JSON: это обнаружится активной проверкой.
   CONNECT определён в [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.3.6).
   MASQUE [CONNECT-UDP, RFC 9298](https://www.rfc-editor.org/rfc/rfc9298.html) нужен
   отдельно для UDP-датаграмм; он не заменяет надёжную доставку текущих TCP-потоков.
2. Использовать поддерживаемый HTTPS frontend с обычным поведением на запросы без
   аутентификации. Туннель допускается только после проверки владельца; закрытый
   адрес/путь сам по себе не заменяет ключ. В качестве референса смотреть подход
   [WebTunnel Tor Project](https://blog.torproject.org/introducing-webtunnel-evading-censorship-by-hiding-in-plain-sight/).
   Это референс архитектуры, не обещание неотличимости или готовая совместимость.
3. Рассмотреть ECH: [RFC 9849](https://www.rfc-editor.org/rfc/rfc9849.html) уже
   стандартизован в марте 2026 и защищает внутренние SNI/ALPN. Нужны реальная
   поддержка обоих концов, безопасное получение ECHConfig и корректная обработка
   отказов. У установленного Python 3.12.8 ECH API отсутствует. При выделенном IP
   единственного VPS скрытие имени не скрывает сам адрес назначения и может давать
   ограниченный выигрыш. DNS-bootstrap также надо учитывать отдельно.
4. Уменьшить повторяющийся рисунок: использовать активный канал для измерений,
   делать standby-пробы адаптивно и реже при стабильной сети, вводить ограниченный
   jitter, отправлять heartbeat преимущественно при простое. Таймауты согласовать
   с реальным RTT и его вариацией, чтобы это не ухудшило восстановление.
5. Исследовать padding по классам размеров и ограниченное изменение времён отправки.
   Заранее задать бюджет лишних байтов и задержки. Добавление случайного мусора
   без модели наблюдателя не доказывает защиту от анализа. TLS допускает padding,
   но размеры и время всё равно важны ([RFC 8446, приложение E.4](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-E.4)).
6. Сравнивать захваты на выходе клиента, а не только внутренние логи. Измерять
   пассивную классифицируемость и ответы на активные пробы относительно обычного
   HTTP-сервиса. Даже хороший HTTPS carrier не скрывает выделенный IP VPS, объём
   передачи или корреляцию входящего и исходящего трафика глобальным наблюдателем.

HTTPS frontend становится частью доверенной стороны, если завершает TLS и видит
открытые данные. При использовании стороннего CDN/relay потребуется внутренний
end-to-end защищённый канал до нашего узла выхода, иначе доверенная граница изменится.
Подмена SNI чужим именем с отключённой проверкой сертификата неприемлема.

**Усиление криптографической эксплуатации**

Обновить Python и используемый TCP OpenSSL через поддерживаемую сборку, пересоздать
venv и повторить матрицу тестов. Сейчас Windows TCP-стек использует OpenSSL 3.0.15
из 2024 года, независимо от нового OpenSSL в wheel cryptography. Доступны последующие
security-релизы Python ([Python 3.12.16](https://www.python.org/downloads/release/python-31216/))
и исправления OpenSSL ([официальные advisories](https://www.openssl-library.org/news/vulnerabilities-3.0/)).
Эксплуатируемость конкретного CVE для этой конфигурации здесь не установлена;
нулевой результат pip-audit не распространяется на эти компоненты. Не заменять
отдельные SSL DLL вручную без согласованной поддерживаемой сборки.

В нашем коде нет бюджета зашифрованных пакетов на ключ и политики ротации длительных
каналов. В просмотренном aioquic есть ручной `request_key_update()`, но автоматическое
достижение AEAD limits отдельной нагрузочной проверкой не исследовано. До эксплуатации
долгих сессий нужно установить владельца счётчиков, проверить поведение backend и
гарантировать обновление/закрытие до лимитов. Для AES-GCM RFC задаёт базовый предел
2^23 пакетов на ключ и допускает иные обоснованные пределы при ограничении размеров
([RFC 9001, §6.6](https://www.rfc-editor.org/rfc/rfc9001.html#section-6.6)). Превышение
такого бюджета — потеря требуемого криптографического запаса, не автоматическая
расшифровка всего трафика. Нужна проверка со сниженным тестовым порогом, без миллиардов
реальных пакетов. Надёжное возобновление позволяет безопасно обновлять сам транспорт.

Затем добавить жизненный цикл ключей: идентификатор устройства/ключа, отзыв,
смену общего ключа без неограниченной поддержки старого и ограниченный срок resume
credentials. Индивидуальная аутентификация устройств нужна при нескольких владельцах;
способ выбирается с учётом реальной поддержки TCP и QUIC backend. Сохранить проверку
сертификата/hostname, отсутствие plaintext-fallback, отключённый 0-RTT для команд
возобновления и запрет экспорта traffic secrets. Наш собственный шифр не требуется.

Lock-файл фиксирует версии без хешей дистрибутивов. Для выпуска добавить хеши,
проверяемое происхождение сборок и SBOM; обновления проверять отдельно на каждой ОС.
Приватные API aioquic в адаптере увеличивают риск несовместимых security-обновлений.

**Практическая последовательность следующей реализации**

1. Исправить A01–A05. Каждое воспроизведение превратить в тест требуемого безопасного
   поведения. Добавить безусловный deadline аутентификации и бюджеты до application
   events. После этого проверить отмены и все перестановки handshake-событий.
2. Сделать публикацию проб независимой, изолировать ошибки кандидатов, добавить
   полный перебор A/AAAA, независимые окна потоков и ограниченный control channel.
3. Ввести один прогретый, уже аутентифицированный standby-канал. Он не передаёт
   DATA до отдельного ACTIVATE/commit и не владеет сессией; количество standby строго
   ограничено. Один атомарный владелец транспорта, растущие поколения, сохранение
   уже принятых Session Manager событий. Это сокращает переключение, но не устраняет
   время обнаружения отказа или полный отказ узла выхода.
4. Добавить настоящий HTTPS carrier, затем ECH при наличии стека, затем измеряемый
   padding/jitter. Каждое улучшение проверять на доступность, задержку и накладные байты.
   Без устранения явного ALPN дальнейший подбор размеров пакетов даёт мало пользы.
5. Для полного VPN отдельно реализовать TUN, маршрутизацию IPv4/IPv6, DNS-политику
   и системный kill switch. Текущий port forwarder не контролирует прямой трафик
   остальных приложений. Egress между VPS требует постоянного живого anchor;
   потерю произвольного исходящего TCP-сокета при падении anchor нельзя скрыть
   одной репликацией SessionID и буферов.

**Следующая матрица проверок**

- Случайные разрывы на каждом сообщении HELLO/WELCOME/READY/READY_OK/ACK/FIN;
  конкурентные переподключения, отмены, потеря последнего подтверждения.
- Сверка байтов и состояний со строго возрастающими offsets, отсутствие повторного
  открытия назначения, отдельные штатные FIN и аварийные RST.
- Замерший поток рядом с активным SSH/загрузкой; ограничение памяти по всем слоям,
  в том числе по QUIC reassembly и незавершённым handshake.
- Потери, задержки, reorder, дублирование, ограничение полосы, UDP blackhole,
  асимметричный путь, DNS с неисправным первым IPv6 и рабочим IPv4.
- NAT rebinding, смена Wi-Fi/мобильной сети, sleep/resume, нагрузка event loop,
  повторение на Windows и Linux.
- Неавторизованные TLS/QUIC-партнёры, попытки удерживать слоты, ложные ранние close,
  повреждённые пакеты, ошибочные сертификаты, ограниченный parser fuzzing.
- p50/p95/p99 времени восстановления; goodput; максимум RAM; лишние байты;
  активные/ожидающие рукопожатия; доля ложных переключений; снимки внешнего трафика.

Для логов добавить фазы подключения, причину отказа отдельно для каждого кандидата,
snapshot метрик выбора, reassembly/queue bytes, ACK-progress, event-loop lag,
завершённое и зарезервированное поколение, причины FIN/RST. Payload и секреты
по-прежнему не нужны. Для DEBUG нужны ограничение хранения и права владельца.
